# Placepick 개발팀 오케스트레이터

## 실행 모드: 서브 에이전트 (팀 아님)

이 프로젝트는 한 사람이 한 대화 안에서 순차적으로 작업을 지시하는 패턴이 압도적으로 많다 — 백엔드 따로, 프론트엔드 따로, 검증 따로, 대부분 한 번에 한 도메인만 건드린다. 여러 전문가가 실시간으로 대화하며 조율해야 할 만큼 서로 얽힌 작업이 드물기 때문에, `TeamCreate`/`SendMessage` 팀 대신 **`Agent` 도구로 서브 에이전트를 직접 호출**하고 결과를 이 스킬(오케스트레이터)이 수집한다. 백엔드+프론트엔드를 동시에 건드리는 기능(예: 새 API + 새 화면)일 때만 두 에이전트를 `run_in_background: true`로 병렬 호출한다.

## Phase 0: 컨텍스트 확인

1. 요청이 새 작업인지, 이전 작업의 후속(재실행/부분 수정/이어서)인지 판단한다.
2. 후속 작업이면 무엇이 이미 바뀌었는지 먼저 확인한다 — `git status`/`git diff`, 그리고 관련 있으면 `docs/decisions.md`(백엔드) 또는 `docs/design-spec.md`(프론트엔드)의 최신 섹션을 읽는다.
3. 범위가 불확실하거나 되돌리기 어려운 변경(스키마 변경, 기존 동작 크게 바꾸기)이면, 구현에 들어가기 전에 프로젝트의 `plan` 스킬 절차를 따른다 — 이 오케스트레이터가 대신 판단해서 넘어가지 않는다.

## Phase 1: 요청 분석 → 도메인 판별

요청 내용으로 어떤 에이전트가 필요한지 정한다:

| 요청 성격 | 필요한 에이전트 |
|---|---|
| API 응답, 추출/검증 로직, 검색 속도·정확도 | `backend-engineer` |
| 화면, 스타일, 레이아웃, 컴포넌트 | `frontend-designer` |
| 둘 다 걸린 새 기능(새 API + 새 화면) | 둘 다 (병렬) |
| "검증만 해줘"/"확인해줘" | `qa-verifier`만 |

## Phase 2: 디스패치

```
Agent(subagent_type: "backend-engineer", model: "opus", prompt: "<구체적 작업 설명>")
Agent(subagent_type: "frontend-designer", model: "opus", prompt: "<구체적 작업 설명>")
```

두 도메인이 다 필요하면 두 호출을 같은 메시지에서 `run_in_background: true`로 병렬 실행하고 결과를 기다린다. 한쪽이 다른 쪽의 산출물(예: 새 API 필드명)에 의존하면 병렬 대신 순차로 — 백엔드 먼저, 결과를 프론트엔드 에이전트의 프롬프트에 포함시켜 전달한다.

## Phase 3: 검증

구현이 끝나면 항상 `qa-verifier`를 호출한다:

```
Agent(subagent_type: "qa-verifier", model: "opus", prompt: "<무엇이 바뀌었는지, 무엇을 확인해야 하는지>")
```

`qa-verifier`가 문제를 찾으면, 원인이 명확한 에이전트에게 재현 방법과 함께 다시 넘긴다(1회). 두 번째도 실패하면 사람에게 그대로 보고한다 — 조용히 넘어가지 않는다.

## Phase 4: 커밋/푸시

이 오케스트레이터는 커밋/푸시를 직접 하지 않는다. 검증을 통과하면 프로젝트의 `commit-and-push` 스킬 절차(검증 통과 시 자동 커밋, 푸시는 사람 승인 후)를 그대로 따른다.

## 에러 핸들링

- 서브 에이전트 호출이 실패하거나 응답이 없으면 1회 재시도한다.
- 재시도도 실패하면 해당 도메인 없이 진행하되, 무엇이 빠졌는지 최종 보고에 명시한다.
- 상충하는 결과(예: 백엔드는 됐다는데 QA가 실패라고 하는 경우)는 임의로 하나를 지우지 않고 둘 다 사람에게 보여준다.

## 테스트 시나리오

**정상 흐름**: "성수동 카페 검색이 느려" → Phase 1에서 backend-engineer 판별 → 디스패치 → pytest 통과 → qa-verifier가 실제 키워드로 재검증 → 통과 → commit-and-push 스킬로 커밋 제안.

**에러 흐름**: backend-engineer가 수정했지만 qa-verifier가 실제 검색에서 회귀를 발견 → backend-engineer에게 재현 방법과 함께 재위임 → 재수정 → 재검증 → 통과하면 진행, 또 실패하면 사람에게 두 결과 모두 보고.
