# Placepick 검증 절차

코드가 맞아 보이는 것과 실제로 그렇게 동작하는 것은 다르다. 이 프로젝트에서 여러 번 확인됐다 — 배치 크기 가설, tier 스케일링 효과, nginx 502 원인 전부 실제로 돌려보고서야 진짜 원인이 드러났다. 아래 절차 없이 "완료했습니다"라고 말하지 않는다.

## 백엔드 변경 시

1. `cd backend && ../.venv/bin/python -m pytest tests/ -q` — 실패하면 여기서 멈춘다.
2. 수집/추출/검증 로직을 건드렸으면 실제 키워드로 직접 호출한다. `docs/decisions.md`에 검증된 ground truth가 있는 사례를 재사용하면 빠르다:
   - **"신논현 카공"** — 특정 업체(셀렉토) 언급 recall 확인용
   - **"강남 맛집"** — 넓지만 한 지역에 묶이는 검색, results mode 기대
   - **"부산여행"** — 여러 동네에 흩어진 검색, overview mode로 전환되는지 확인
   - **"성수동 브런치"** — 좁은 지역, 빠르게 끝나는지 확인

   결과가 나오기까지 수십 초~수 분 걸릴 수 있다. `run_in_background: true`로 실행하고, 완료될 때까지 폴링한다(`while [ -s logfile ]; do sleep N; done` 패턴).
3. Dockerfile/docker-compose/설정 파일을 건드렸으면 `docker build -t placepick-verify .`로 이미지가 빌드되는지 확인하고 정리한다(`docker rmi`).

## 프론트엔드 변경 시

1. `cd frontend && npm run build` — 실패하면 여기서 멈춘다.
2. 로컬 서버를 재시작한다(`backend/main.py`) — Python 라우트/로직 변경은 정적 파일과 달리 재시작이 필요하다.
3. 실제 브라우저로 화면을 띄우고 검색 흐름(입력 → 로딩 → 결과)을 한 번 실행해서 스크린샷을 남긴다.
4. 가능하면 모바일 폭도 확인한다. 리사이즈 도구가 이 환경에서 불안정할 수 있으니, 안 되면 시도했다는 것과 안 된 이유를 그대로 보고한다 — 확인 안 된 걸 확인됐다고 하지 않는다.

## 보고

실행한 명령과 실제 출력(또는 스크린샷)을 함께 제시한다. "정상 동작할 것으로 보입니다" 같은 표현 대신, 무엇을 실행해서 무엇을 봤는지 말한다.
